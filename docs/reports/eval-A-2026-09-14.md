## 四、成本账

- 总 token 179,732（prompt 122,412 / completion 57,320），预估 **¥0.2527**
- 单问 7,488.8 token（prompt 5,100 / completion 2,388）
- 真实 LLM 调用 **69 次**（24 问，均值 2.88 次/问；常规路径 3 次，触发重试的 q001/q038 为 6 次）

两个放大点：

1. **重试轮**：q001（16,890 tok）与 q038（21,989 tok）两条合计占全部 token 的 **21.6%**，同时也是延迟榜的前两名（99.4s / 152.5s）。verify 判定不达标 → 整段 prompt 重发 → token 与延迟同倍增长。
2. **completion 不设上限**：`answer_prompt` 既无长度约束，answer 节点的 `complete_json`（nodes.py L204）也**没有传 `max_tokens`**（对比 verify 已收紧到 200）。个别回答烧到 2,954 / 3,184 completion token（q004），单次调用 51.0s / 78.6s——**completion 长度就是延迟的第一驱动**，而非调用轮数。

结论：换 `qwen3.8-flash` 只降了**单价**，没降**用量与耗时**。真正的杠杆是"少写（限长）+ 少重试"，价格只是次要变量。

## 七、下一步建议（按性价比排序）

1. **给 answer 限长**（改 1 行 + 1 条 prompt 约束）：`max_tokens≈512` + "先给结论、≤3~5 句"。直击 completion 2388 token/问 这个大头，预计 token 与延迟同时下降一半以上，且不改架构。
2. **兜住零引用**：`_route_after_verify` 增加确定性条件 `len(citations) > 0`，否则按"未达标"走一次重试 → 再走 `disclose`（`_NO_CITE_SUFFIX` 已有）。这是"只做检索+披露"原则目前漏掉的一个口子。
3. **重试要更贵得起**：`retry_hint` 里把上一轮答案一起截断重发，或重试只带 top-3 证据，避免重试期间 prompt 全额重发。
4. **重定 NFR 口径**：全链路 P95 ≤ 8s 在当前"串行三跳 LLM"下不可达，建议拆成 TTFT（首 token ≤ 2~3s）+ 完成 ≤ Xs 两个指标，或明确把 rewrite 降级为规则/缓存以缩短首跳。
5. **noisy 类型**：针对口语化改写做 query 归一化（数字/口语词 → 规范词），这是唯一 recall 全灭的类型。

### 8.7 verify 首过率：现在每问被 verify 打回几次

问题背景：限长之后延迟大头变成"3 次串行 LLM 调用"，而**重试会再叠一轮（rewrite+answer+verify = 3 次调用）**，所以"每问被 verify 打回几次"直接决定成本与延迟的尾巴。此前这个数字只能靠翻评估日志数 `calls=`，现已接进报告。

**口径**（`app/eval/runner.py` → 报告 `verify` 块）：

- 分母只算**真正走到 verify 的题**：kb_qa 首跳 LLM 基线 = 3 次（rewrite + answer + verify），故 `llm_calls ≥ 3` 或 `retries > 0` 才算进分母；chitchat / contact_guidance（0 次 LLM）与 no_data（1 次）不经 verify，不计入。
- 判定次数 = `retries + 1`：末次判定必然发生（通过 → finalize；用尽 → disclose）。
- `retries` 取自终态 `retry_count`（由 retry 节点自增），非日志文本推断。

**两轮同题对照**（同 24 条分层抽样、同配置）：

| 指标 | 第 1 轮（11:56） | 第 2 轮（14:33） |
|---|---|---|
| verify 首过 | 23 / 24 = **0.958** | **24 / 24 = 1.000** |
| 被重试的题 | 1 条（q004，2 次） | 0 条 |
| verify 判定次数 | 26（单问均 1.08） | 24（单问均 1.00） |
| LLM 调用总数 | 78（3.25/问） | 72（**3.00/问**） |
| 引用可回查率 | 0.792 | 0.708 |
| recall@5 / MRR | 0.917 / 0.812 | 0.917 / 0.812 |

结论：**verify 首过率在 96%~100% 之间波动（同一题 q004 上一轮被打回 2 次、这一轮一次过）**，重试不是延迟与成本的主导项——两轮 72~78 次调用里重试只占 0~6 次。真正的尾巴在别处（见下）。注意 verify 判"过" ≠ 引用站得住：第 2 轮 verify 全过，但引用可回查率只有 0.708（该指标分母用的是**原始查询**的检索命中集，而 answer 用的是**改写后**查询，两者不同源，故它会低估，不能直接当作 verify 失职的证据）。

### 8.8 复跑暴露的另一个事实：p95 由供应商侧长尾主导

第 2 轮 p50 与第 1 轮一致（6,363 ms vs 6,176 ms），但 p95 从 **11,050 ms 恶化到 37,775 ms**、max 到 55,299 ms。逐题归因后**与重试无关**（该轮 0 重试、每题恰好 3 次调用）：

| 题 | 单问耗时 | 归因 |
|---|---|---|
| q039 | 55,299 ms | 其中**一次 `complete_json` 单调用耗时 49,431 ms**，prompt 仅 329 token、completion 仅 28 token |
| q012 | 37,775 ms | 其中**一次 `complete_json` 单调用耗时 33,844 ms**，completion 仅 27 token |

两次都是"输入极小、输出极小、却耗时 30~50 秒"的**供应商侧排队/首 token 停顿**，不是我们的 prompt 变长或链路多跑。剔除这 2 条后 p95 回落到 8,152 ms。

含义：**NFR 用"p95 全链路 ≤ 8s"一个数把两类完全不同的问题混在一起了**——一类是我们能优化的（串行调用数、prompt 体积），另一类是供应商长尾（只能靠超时+降级/重试策略兜）。建议 NFR 拆成三档并分别定阈：① TTFT（流式首 token）；② 排除供应商停顿后的完成时长；③ 供应商停顿率/兜底行为（超时阈值、超时后是否必须仍给出可披露的答案）。

### 9.5 顺带修掉的指标 bug：`reached_verify` 靠"调用次数"猜

本轮第一次跑出现 `校验: verify 首过 0/4 = 0.000`、`reached_verify: 4`，与逐题 `retries`
（20 条 0 重试）自相矛盾。根因：判据写死为 `llm_calls >= 3`（旧的 rewrite+answer+verify 三跳基线），
而 rewrite 规则短路后正常题只有 2 跳 → **20/24 条正常题被误判成"未经过 verify"**，首过率显示为 0。

修法：判据改为**读取状态痕迹** —— `reply()` 从终态 notes 取 `verify:` 前缀写入
`AgentApp.last_verified`，评估侧消费该标记，`per_case` 增 `verified` 字段。
修后 `verified dist: {True: 24}`、首过 21/24。

教训：**指标判据必须来自状态痕迹，不能来自次数猜测** —— 次数基线会随性能优化（如 rewrite 短路）失效，
而且失效时是"静默错报"，不报错、只是数字变假。

### 9.6 评估口径修正：`eval:{case.id}` 的 thread 历史残留

实测（同一 thread 连跑 3 次同一问题）：

| 第几次 | LLM 调用 | rewrite 走向 |
|---|---|---|
| 1（冷启动） | **2** | notes 记「原样透传（规则短路）」 |
| 2 | **3** | 真实调用 rewrite |
| 3 | **3** | 真实调用 rewrite |

原因：评估 thread_id 固定为 `{tenant}:eval:{case.id}` + Redis checkpointer → 上一轮评估的
messages 被残留进来 → `_history` 非空 → `should_skip_rewrite` 恒返回 False（其规则是"有历史就重写"）。

影响：**同一批题，第 N 次跑比第 1 次贵**（多一跳 rewrite + 一段无关 history），
指标随"跑第几次"漂移，历轮"改前 vs 改后"的对比因此不公平。

修法：`runner.py` 的 thread_id 加**本次运行盐值**（`eval:{run_salt}:{case.id}`）→ 每次都冷启动、指标可比。

附带结论：`should_skip_rewrite` 的"有历史就一律重写"过激 —— 全量 55 条中 **93%** 的 query
本身不含指代。应改为「有历史 **且** 本句含指代/省略」才改写。
