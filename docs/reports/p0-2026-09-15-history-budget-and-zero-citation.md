# P0 报告：history 预算限长 + 长历史样本 + 零引用判据（2026-09-15）

> 背景：2026-09-14 的多轮评估结束后，待办清单里剩三项"有数据支撑、不做会埋雷"的 P0：
> ① `render_history` 限长；② 补长历史样本（没有它 ① 无法验证）；③ 零引用是否算未达标。
> 本报告记录三项的落地方式、验证结果与已知偏差。三项是**一个闭环**：样本是 ① 的验收工具，
> ① 让样本可成本化，③ 顺手补上 verify 出口上最后一个洞。

---

## 1. 为什么必须先做样本、再做限长（顺序不能反）

`render_history` 的旧实现只受两个约束：窗口 `max_rounds=10` 与每条 `[:300]` 字。
上限 = 10 轮 × 2 条 × 300 字 = **6,000 字/次注入**；而历史在链路里被注入**两次**
（rewrite 一跳 + answer 一跳；verify 刻意不注入）→ 最坏 **≈7,500 tok/问**，
约等于单问 prompt（≈3,200 tok）的 2.3 倍。

这个风险之所以能躲过九轮评估，是两个口径问题叠在一起：

| 看不见的原因 | 说明 |
|---|---|
| 单轮集无历史 | history 项恒为 0，结构上不可能暴露 |
| 多轮样本每条只有 **2 轮** | 2 轮 = 4 条消息，恰在窗口（10 轮）与单条上限（300 字）**阈值之下**，两级截断都不会触发 |

所以 2026-09-15 的动作是**先造能触发的样本，再改限长**——反过来的话，改完既没有样本能验证，
也不知道有没有改坏（比如把"最新一轮"一起截掉，指代直接解析错）。

## 2. 改动 ①：`render_history` 两级预算

`app/agent/prompts.py::render_history` 由"纯窗口 + 每条截断"改为**两级预算，从最新往旧累积**：

```
render_history(messages, max_rounds=10, *, per_msg_chars=None, total_chars=None)
  ├─ 每条先截到 per_msg_chars（默认 HISTORY_PER_MSG_CHARS=150）
  ├─ 再按 total_chars（默认 HISTORY_TOTAL_CHARS=1200）从**最新往旧**累积，超出即停
  └─ 兜底：`picked` 非空才允许因预算 break → 单条超预算时至少留一条，绝不返回空历史
```

设计要点：

- **为什么从最新往旧**：指代消解依赖的是**最近上文**（m006 的末轮就靠紧邻上一轮补全），
  丢最旧的代价最小；反过来做会把最有用的那次注入砍掉，等于用成本换了个更差的检索。
- **窗口退化为安全网**：预算（1,200 字）先于轮数窗口（10 轮 × 2 × 150 = 3,000 字）生效，
  所以实际绑定的是总量预算。这一点用零 LLM 的单元断言锁定，而不是造 11 轮真跑样本
  （30+ 次 LLM 调用换一条断言，不划算）。
- 单次注入上限 ≈1,200 字 ≈ 710 tok，两次 ≈ **1,400 tok/问**（原上限 7,500 → 降 ~81%）。

配置项（`.env.example` / `docker-compose.yml` 白名单 / `docs/deployment.md` 三处同步）：
`HISTORY_PER_MSG_CHARS=150`、`HISTORY_TOTAL_CHARS=1200`。

> 顺带修掉一个**早有约定的漏登记**：`QA_CONFIDENCE_THRESHOLD` / `QA_MAX_RETRY` /
> `QA_HISTORY_ROUNDS` 三项一直没进 compose 白名单 → 容器内只能吃应用默认值、改不动。

## 3. 改动 ②：长历史样本（5 条 → 7 条）

`data/golden/qa_golden_multiturn.json` 新增两条长历史样本，历史轮刻意横跨 6~7 份文档：

| id | 类别 | 轮数 | 末轮 | 未截断体量 | 截断情况 | 考的是什么 |
|---|---|---|---|---|---|---|
| **m006** | ellipsis | 8（7 历史轮） | 「部门经理的标准是多少？」 | 619 字 | **无截断**（< 1,200，per-msg 也没触顶） | 末轮靠**紧邻上一轮**（出差住宿标准）补全 → 长上下文里判据不退化、且能正确定向到最近那一轮 |
| **m007** | independent | 11（10 历史轮） | 「员工食堂这周的菜单是什么？」 | **1,503 字** | **总量预算绑定** → 渲染 1,182 字、最早 2 轮被丢 | 长历史下末轮**仍应跳过改写**（白名单回归防线）+ 截断方向「优先丢最旧、保留最新」+ 轮数恰为窗口上限，故只可能由预算触发 |

两条锚句已核实**唯一命中**（`部门经理 | 一线城市 | 1100/天` → 1 块；`周一：红烧排骨、清炒时蔬` → 1 块）。
meta 里新增 `history_axis` 说明 short/long 两轴分工，并把「11 轮以上窗口截断未覆盖、改用单元断言锁定」写进 `known_limitation`。

### 3.1 ⚠ 复测修正：初版「8 轮必然触发总量预算」是错的

初版两条样本都是 8 轮，note 里断言「累计历史必然超过 1,200 字预算、截断必然发生在末轮之前」。
**2026-09-15 复测证明该断言错误**：

- 真实答案平均约 90 字（不是 300 字上限），8 轮只累计到 **606~1,030 字**，**从未触达 1,200**；
- 8 轮真正能触发的只有 **per-msg 150 字**上限（m007 出现 4 行恰好 150 字 = 前缀 4 + 150，答案被硬截在「[来源:」处）。

更关键的是：**m006 的断言价值恰恰在「截断方向」，而它根本没被截断过**——等于没测到点子上。
故把 m007 由 8 轮加长到 **10 个历史轮**（11 轮）：

| 指标 | 值 |
|---|---|
| 历史轮数 / 消息数 | 10 轮 / 20 条 = **轮数窗口上限** → `msgs[-20:]` 不裁剪，排除窗口干扰 |
| 未截断体量 | **1,503 字 > 1,200** → 总量预算**真实绑定** |
| 渲染结果 | **1,182 字**，丢掉的正是**最早的 2 轮**（差旅住宿标准 / 市内交通补贴） |
| 结论 | ✅ 截断方向确认「优先丢最旧、最新一轮完整保留」 |

m006 保持 8 轮不动，作为「长历史但**未**被截断」的对照下界——两条合起来才构成
complete 的两级截断验证；这是本轮 P0 唯一一处**先做错、复测发现、再修正**的地方。

## 4. 改动 ③：零引用 = 未达标（确定性 + 0 LLM 短路）

`app/agent/nodes.py::verify` 原先的兜底是"零引用 → 回退全量证据照常判定"，
于是模型只要说 `grounded=true` 就能让一条**没有任何出处**的答案直接出货（q007 有前科）。
而 `disclose` 里那支 `_NO_CITE_SUFFIX`（"未能在现有知识库中找到对应出处，请勿直接作为依据"）
因为几乎走不到，**基本是死代码**。

改为：

```python
cited_ids = {c["chunk_id"] for c in state["citations"] if c["chunk_id"]}
if not cited_ids:                      # 零引用
    return {"grounded": False, "confidence": 0.0, ...}   # 不调 LLM
```

依据是用户定的出口纪律：四类出口里**凡"给出答案"的出口都必须带出处**
（① 有资料→答案+出处；② 资料不全→现有数据+出处），零引用即"不可回查的裸答案"。
不调 LLM 的理由：答案按构造就不可校验，判定是确定性的，没有可"判"的东西。
落点复用既有出口链：`verify → retry（≤2）→ disclose`。

**已知代价（要认，不是 bug）**：模型如实写"资料里没有这条"时也会被打回重试——
但重试 hint 正是"如实说明资料不足之处与信息来源"，2 轮后落入 disclose，
与出口③「查不到 → 告知缺失」语义一致，只是多花两次往返。

## 5. 改动过程中暴露的一个真问题（已锁定、未修）

加了零引用判据后重试变得常见，于是**撞出**一个既有偏差：verify 打回重试时，
每次 answer 都会重新流式推送，**token 流里留下多次尝试的文本**，而 `done.answer` 只有最后一次。
即"token 拼接 == done.answer（前端零特判）"这条不变式**在重试路径上不成立**。

- 影响面可控：前端在 `done` 处用 `done.answer` **整体覆盖**重渲染（`web/index.html`），
  不会留下错误终态，只是流式中途的瞬态重影；
- 要真正修好需要协议层加 `reset`/`retry` 事件（契约 §2.1 变更），属独立议题；
- 已写成 `verify_sse_streaming.py` 第 4 组的**显式断言**（"重试使 token 流含多次尝试文本（已知偏差，已锁定）"），
  避免它被误当成"已修复"或被后续改动悄悄掩盖。

## 7. 复测抓出的真 bug：单字代词被**子串**误判（已修）

### 7.1 现象

首次跑 7 条多轮评估时，**m007 末轮本应 `skip`，实际却是 `llm` + `identity`**——
即花了一次 LLM 一跳、改写结果**与原文逐字相同**，纯空转。末轮是
「员工食堂**这**周的菜单是什么？」，自带主题锚点（员工食堂 / 菜单），是完全独立的问句。

### 7.2 根因

旧回指判定是**子串**匹配：`any(h in q for h in ("它","这","那",…))`。
「这周」里的「这」被当成指代词 → 判为回指 → 必须改写。同理 `那次`、`其他` 都会误命中。
这正是本项目 2026-09-14 记下的那条教训的另一面：**词表干净才敢用子串匹配**；
反过来，**对"含某字即命中"的判据，必须先问分词边界**。

### 7.3 修法（`app/agent/prompts.py`）

```python
_PRONOUNS = ("它","他","她","这","那","此","其","该")          # 单字：按 jieba 整词判
_PRONOUN_PHRASES = ("这个","那个","这些","那些","上述","前面","刚才","该文档",…)  # 多字：子串判

def _has_anaphora(q):                      # 整词判单字代词 + 子串判多字短语
    if any(p in q for p in _PRONOUN_PHRASES):
        return True
    return any(t in _PRONOUNS for t in _tokens(q))    # _tokens 走 jieba，lru_cache
```

实测 jieba 把 `这周` / `那次` / `这些` 切成整词 → 不再误命中；`这个标准` / `那它` / `该文档`
仍能被正确识别为回指。**代价**：判据现在依赖 jieba 是否把复合词切成整词（缺依赖时
`_tokens` 返回空元组，退化为只判多字短语，偏保守——宁可多改写，不漏消解）。

|---|---|---|
| golden 多轮末轮分类一致 | 5/7（✗m003, m007） | **7/7** |
| 人工探针一致 | 12/12（未含该反例） | **13/13** |

## 8. ⚠ 复测副产物：空转不只在末轮，中间轮同样在烧

评估脚本的 ② 段只统计**末轮**分类，但长会话里**每一轮都是"末轮"**。
把 29 轮全量统计后：

| 指标 | 值 |
|---|---|
| 跳过率（全部轮次） | 21/29 = **72.4%** |
| 空转改写（全部轮次） | **3/29 = 10.3%** |

三条空转的成因**不同**，要分开看：

| 轮次 | query | 字符 | 成因 |
|---|---|---|---|
| m007 第 4 轮 | 年假有多少天？ | 7 | **真判据空转**：被 `len ≤ 8` 短句下限否决，但它自带锚点「年假」，是完整问句 |
| m007 第 5 轮 | 加班费怎么算？ | 7 | **真判据空转**：同样被 `len ≤ 8` 否决；且「加班费」**不在锚点词表**里（文档写的是「加班」，jieba 又切成「加班/费」）→ 即使放宽阈值也仍会被「无锚点」拦住 |
| m007 第 7 轮 | 报销需要提供哪些凭证？ | 11 | **非判据问题**：`retries=2`，重试路径按设计必须改写（要注入"补充引用"提示），空转来自重试改写恰好与原文相同 |
