## 一、P1 问题（逻辑漏洞，已修复）

### R1 · 幂等"身份键"体系自相矛盾（契约 §2.2 ↔ 需求 F1.7/F1.8）

- **问题**：契约写"doc_id 由服务端按 content_hash 派生"，但 F1.7 版本化软更新要求同一文档跨版本保持同一 doc_id。doc_id 若随内容变化，内容一改就成了"新文档"——旧版本永远无法被"取代"，版本化机制整体失效，知识库会无限堆积重复文档。
- **修复**：引入**内容无关的身份键**统一规则：
  - `doc_key`：逻辑文档身份（默认规范化文件名，可经 `meta.doc_key` 显式指定）
  - `doc_id = "doc_" + sha256(tenant_id + ":" + doc_key)[:12]`，跨版本稳定
  - `content_hash`：仅作变更指纹与幂等检测，**禁止**参与 doc_id 派生
  - Registry 主键改为 `(tenant_id, doc_key)`，上传分流：新 doc_key→新建；同 key 同 hash done→幂等 200；同 key 同 hash processing→409；同 key 异 hash→版本化更新
- **落点**：需求 F1.8（身份说明块 + 判定规则表 + 状态机）、F1.1 边界、7.1 doc_id 注释与机制映射；契约 §2.2 字段表/响应表/身份规则注、§3 INGEST_IN_PROGRESS 触发条件、§4.7 DocRegistry 签名。

### R2 · `effective_time=0` 的永久文档会被检索永远排除（需求 F2.8 ↔ 契约 4.5）

- **问题**：原 where 为 `{"effective_time": {"$gte": now}}`，"0/缺省=永久"的文档要么字段缺失、要么为 0，多数向量库对"无该字段或小于 now"的记录不匹配该操作符 → **所有永久有效文档不可召回**，属灾难级默认行为。
- **修复**：统一约定——永久文档写入时 `effective_time` **一律写 0 且字段不可缺失**；检索 where 改为 `{"$or": [{"effective_time": {"$eq": 0}}, {"effective_time": {"$gte": now}}]}`，向量/BM25 双侧一致。
- **落点**：需求 F2.8 实现要点；契约 §4.5 过滤构造示例。

### R3 · 错误体字段名跨文档不一致：`trace_id` vs `request_id`

- **问题**：需求 6.3 示例与 NFR 用 `trace_id`，契约 1.5 与所有响应头用 `request_id`（且 SSE done 也用 request_id）。客户端若按契约解析会拿不到字段。
- **修复**：全链路统一 **`request_id`**（与 `X-Request-Id` 头呼应）。
- **落点**：需求 6.3 示例、NFR 可观测性行。

## 四、遗留观察项（未改文档，供决策）

1. **验收标准第 1 条**要求上传含"图文混排 PDF 至少 1 份"，但图像内容描述（VLM）在 backlog——建议实现时明确该条只要求**文本部分**可被索引检索，图像描述不阻塞验收（或把验收词改为"含扫描/图文 PDF 至少 1 份，文本部分可检索"）。
2. **history 分页**契约只有 `limit` 无游标——单线程历史很短够用；若未来接入长会话建议补 `cursor`，暂不必要。
